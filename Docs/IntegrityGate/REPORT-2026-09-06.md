The concrete defect was the serialized script reference. All three components referenced scene-local `m_Script: {fileID: 1487154252}`, an embedded MonoScript naming DeliveryCrate, rather than an imported script asset with a GUID. Its asset path was empty. DeliveryCrate was a second MonoBehaviour-derived class inside FixtureDelivery.cs; DeliveryCrate.cs and its .meta did not exist. FixtureDelivery.cs.meta had GUID `94aa8389180204879b1495a594632039`, and its imported MonoScript resolved FixtureDelivery. Unity documents that, when a script contains multiple classes, the class matching the filename is selected. [Unity 6.6 script naming](https://docs.unity3d.com/6000.6/Documentation/Manual/naming-scripts.html).

FixtureDelivery.Refresh binds slots and toggles active state; it does not remove these components. Reproduction before Play and in a fresh preview scene rules out intentional runtime removal and an MCP-only readback failure. The existing native MonoScript reference made the zero missing-script counts insufficient evidence of healthy managed binding. This establishes a project serialization defect; the evidence does not establish a Unity 6.6 regression or justify recording the original result as a stale domain artifact.

The repair moved DeliveryCrate unchanged into its own file and rebound the three existing components through Unity SerializedObject APIs, preserving all object and component file IDs. The new script GUID is `7278791689a2a466ba98fe248067bacf`. All component arrays now contain Transform and DeliveryCrate, all typed lookups succeed, and all native missing-script counts remain zero. Fresh scene loading, a second full Editor restart, and subsequent Play cycles passed with the original DisableDomainReload and DisableSceneReload options still enabled.

Workshop's final diff is exactly three script-reference replacements and removal of the embedded MonoScript: 3 inserted lines, 18 deleted lines. Incidental URP light-component additions were removed through Unity before the intentional scene save. No other production scene was saved. Scene SHA-256 values:

The original half-collider generator sampled every fourth longitude and third latitude, producing 241 vertices and 456 input triangles. Re-baking that original construction reproduced the partial-hull warning on seed 62's top half. There was also a second cooking trigger: adding MeshCollider to a half initially assigned its MeshFilter's detailed visual shell. AddHalfCollider now clears that automatic mesh before enabling convex cooking and assigning the collision proxy.

The replacement collision mesh selects the outermost point from each of 16 angular sectors in 8 exterior bands, plus the pole. It has 129 vertices and 254 input triangles, including a flat fracture-plane cap. A convex hull of 129 vertices has at most 254 triangular faces, below Unity's documented 255-triangle ceiling. The visual fracture mesh is unchanged. [Unity 6.6 MeshCollider reference](https://docs.unity3d.com/6000.6/Documentation/Manual/class-MeshCollider.html).

Flat opposing caps prevent closed convex halves from overlapping across the jagged visual seam. Opened poses now use the actual proxy extents and a 4 mm separating gap, because mean-radius spacing could intersect on strongly knobbled specimens. The correction also applies to saved open poses. Reveal reuses the existing cooked colliders.
